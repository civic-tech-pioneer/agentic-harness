Slice: S34 — scope keys for session allows: a session allow holds one (tool, scope key), computed afresh from the input that will run

## Goal

A session allow is a pair (tool, scope key). After this task each tool that
has a scope function in `kernel/src/broker.rs` turns a Claude ask's input
into its key (Bash: the exact command with its pins; the file tools, now with
`MultiEdit`: the workspace; `WebFetch`: the URL's host after one WHATWG
parse; `Skill`: the skill's name; `TodoWrite`: empty); every other tool,
`mcp__watane__<tool>` now among them, and any input with a key its function
does not know, gets no key and always asks. The ask shows the key as `reach`
(`<Tool>(<key>)`, bare `<Tool>` for an empty key); `for: session` stores
`{id, tool, key}`; a later ask is answered `session-allow` only when the key
computed afresh from its own input equals a stored pair exactly.

**The rule (the human, 2026-11-21, quoted; it is the rule):** "(2) Session
allows use a scope key per tool: a pure scope function turns a call's input
into the smallest part that decides what it can reach and that a person can
judge at a glance (Bash: the exact command; file edits: the workspace; a web
fetch: the host; a skill: its name). A tool without one, or an input that
cannot be scoped safely, gets no key and always asks. The kernel computes the
key from the input that will run and shows it on the ask; 'allow for this
session' stores (tool, key); a later call is allowed only when its fresh key
equals a stored pair exactly; take-back and session end remove it. (3) Bash:
the exact command. (4) The sandbox is the boundary for Bash allow rules."

**The spec (TECHNICAL 9.6, written by the foreman for S34; read it whole):**
"Session allows: scope keys" with its table, and "As built (S34): the scope
functions" (Known keys, Files, Bash, WebFetch, Skill, TodoWrite; then "An
allow is `{id, tool, key}`"). Quoted, the parts that change code:

> | `Bash` | `command`, `description`, `timeout`, `run_in_background` | the exact command; then `; timeout=<n>` and `; run_in_background=<true\|false>` when the input has them (pinned, S33) |
> | `Edit`, `Write`, `MultiEdit`, `NotebookEdit`, `Read`, `Glob`, `Grep` | the fields of that tool's input (below) | the workspace, `<ws>/**` |
> | `WebFetch` | `url`, `prompt` | `domain:<host>`, the URL's host after one parse |
> | `Skill` | `skill`, `args` | the skill's name |
> | `TodoWrite` | `todos` | empty (reach `TodoWrite`): it reaches nothing outside the session |
>
> Every other tool has no scope function and always asks: `Task` and
> `WebSearch` [...], `AskUserQuestion` and `ExitPlanMode`, and
> `mcp__watane__<tool>` until that tool names its own key (14). An input
> with a key the tool's scope function does not know gets no key (file
> tools too: the `_host` key [...]), as does any value outside the rules below.

> *Known keys.* The input is a JSON object whose every key is one the
> tool's row knows. The file tools know: `Read` `file_path`, `offset`,
> `limit`, `pages`; `Write` `file_path`, `content`; `Edit` `file_path`,
> `old_string`, `new_string`, `replace_all`; `MultiEdit` `file_path`,
> `edits`; `NotebookEdit` `notebook_path`, `new_source`, `cell_id`,
> `cell_type`, `edit_mode`; `Glob` `pattern`, `path`; `Grep` `pattern`,
> `path`, `glob`, `type`, `output_mode`, `-A`, `-B`, `-C`, `-n`, `-i`,
> `multiline`, `head_limit`, `offset`. Values of keys that are not part
> of the key are not read.

> *Bash.* `command` is a string with no `:`, and `Bash(<command>)`
> passes the 4.1 allow grammar (so it has no `;` or `)`); then
> `timeout`, when present, is a JSON integer from 0 to 2^64-1, written
> in decimal, and `run_in_background`, when present, a JSON boolean. Key
> `<command>`, then `; timeout=<n>`, then `; run_in_background=<b>`,
> each only when the input has it, in that order: reach `Bash(ls;
> timeout=5; run_in_background=true)`.

> *WebFetch.* `url` is a string of 1 to 2 048 bytes, printable ASCII
> only (no space, no control character, no `\`), parsed once as a
> WHATWG URL (the `url` crate, as Node's `URL` that `claude` runs); the
> parse succeeds, the scheme is `http` or `https`, there is no username
> or password, no port other than the scheme's default (which the parser
> drops), and the host is a domain or an IP address with no `(` or `)`.
> Key `domain:<host>`, the parsed host as the parser writes it
> (lowercase; a non-ASCII name as its `xn--` form): reach
> `WebFetch(domain:example.com)`. [...] an allow holds that host only,
> never another one, a subdomain or a parent.

> *Skill.* `skill` is a name `[a-z0-9-]{1,64}`, or two such names joined
> by one `:` (a plugin's skill). Key the name: reach `Skill(pdf)`.
> `args` is not part of it.

> An allow is `{id, tool, key}`; its id is the index of its `given: true`
> entry. An answer `for: session` to an ask with no key is refused
> `{field: "decision"}`; one whose pair is already held adds nothing and
> writes no entry.

9.4, the `allow` entry (changed): `{"id","tool","key","reach","given","by"}`;
`reach` is the one its ask showed, `<tool>(<key>)`. The console reads only
`id`, `reach`, `given`, `by`: keep them.

**9.3 "Past" (quoted, this task changes what `answer for: session` and
`take-back` write):** "Past the kernel's 224 MiB account (or an owner's quota)
only these writes go on, into the reserve: the entry and turn state that
record a stop, ask decisions (including denials by expiry), `stream/` and
`live/` keys of an `attach`, slot and timer counts, and every `delete`.
`rename`, a session allow (`for: session`) and new input are refused
`quota`; so is everything else past the account." and 9.6: "`take-back` [...]
reads no `access/` and is never refused `quota` (it only narrows; its entry
is charged like the calls of 9.3 "Past" that cannot fail)." Nothing about
that changes: the allow entry grows by its `tool` and `key` only.

Design inside the task (fixed here): `broker::scope(tool, workspace, input)
-> Option<String>` returns the key; `broker::reach(owner, workspace, kind,
tool, input) -> Option<String>` stays, returns `render(tool, key)` and keeps
its owner/kind checks; `broker::render(tool, key)` is `<tool>(<key>)` or the
bare tool for an empty key. `sessions.rs` matches a new ask by computing
`scope` afresh from that ask's tool and input (not by reading its `reach`)
and comparing `(tool, key)` with `rec.allows`; `answer for: session`
computes the pair afresh from the stored ask entry's `toolCall.title` /
tool and `input` the same way. Add `url` to `kernel/Cargo.toml` with an exact
`=2.5.x` pin (it builds for wasm32-wasip2 with its default features).

## Acceptance

AC1. Unit (`tests/it/broker.rs`): `scope`/`reach` for Bash:
`{"command":"ls"}` -> `Bash(ls)`; with `"timeout":5` -> `Bash(ls; timeout=5)`;
with both pins and a description -> `Bash(ls; timeout=5; run_in_background=true)`
whatever the key order; `dangerouslyDisableSandbox` or any other key -> none;
`timeout` of `-1`, `1.5`, `"5"` -> none; a command with `:`, `;` or `)` -> none.
AC2. Unit, file tools with workspace `/w`: `Edit`, `Write`, `MultiEdit`,
`NotebookEdit` (`notebook_path`), `Read` on `/w/a/b.rs` -> `<Tool>(/w/**)`
with every known key of the row present; the same input plus `"_host":"x"`
(or any unknown key) -> none; `/w/../etc`, `/w/./a`, `/w//a`, `/etc/x`,
`/wx/a` -> none; no workspace -> none; Glob rules of S33-fix1 unchanged.
AC3. Unit, WebFetch: `https://Example.COM/a?b` -> `WebFetch(domain:example.com)`;
`http://example.com` -> the same key; `https://example.com:443/` -> the same;
`https://example.com:8443/` -> none; `https://u:p@example.com/` and
`https://u@example.com` -> none; `ftp://example.com`, `file:///etc/passwd`,
`javascript:x`, `example.com` (no scheme), `""`, a URL with a space, a tab, a
`\`, a non-ASCII byte, or over 2 048 bytes -> none; `https://bücher.de` written
with non-ASCII -> none (not printable ASCII), `https://xn--bcher-kva.de` ->
`WebFetch(domain:xn--bcher-kva.de)`; `https://127.0.0.1/` ->
`WebFetch(domain:127.0.0.1)`; an input with a key other than `url`, `prompt`
-> none; `url` not a string -> none. `https://evil.com#@example.com` and
`https://example.com.evil.com` give the key of the host the parser reads
(`evil.com`, `example.com.evil.com`), never `example.com`.
AC4. Unit, Skill: `{"skill":"pdf"}` and `{"skill":"pdf","args":"x"}` ->
`Skill(pdf)`; `{"skill":"watane-run:pdf"}` -> `Skill(watane-run:pdf)`;
`PDF`, `a:b:c`, `:a`, `a:`, `a b`, `../x`, 65 characters, `""`, a non-string,
an unknown key -> none.
AC5. Unit: `TodoWrite` `{"todos":[]}` -> `TodoWrite`; `{"todos":[],"x":1}` ->
none. `mcp__watane__send`, `Task`, `WebSearch`, `AskUserQuestion`,
`ExitPlanMode`, `Agent`, `mcp__other__x` -> none whatever the input. A check
and an `agent:` owner -> none (unchanged).
AC6. Through the kernel (attached owner, as `allows.rs` does): the owner
answers `{"allow":true,"for":"session"}` to a WebFetch ask on
`https://example.com/a`; a later ask on `https://example.com/other?q=1` is
answered `allow, by: session-allow`; one on `https://api.example.com/` and
one on `https://example.com.evil.com/` open for the owner. The same for Skill
(`pdf` allowed, `pdf2` asks). The `allow` entry body is
`{"id","tool":"WebFetch","key":"domain:example.com","reach":"WebFetch(domain:example.com)","given":true,"by":"owner"}`;
`rec.allows` holds `{id, tool, key}`; `take-back` writes the same body with
`given: false` and the next matching ask opens again.
AC7. Through the kernel: an ask whose stored `reach` was forged or that came

`npm test` does not answer `npm test` with `run_in_background: true`.
AC8. Through the kernel: `for: session` to a `Task`, `WebSearch` or
`mcp__watane__send` ask is refused `{field: "decision"}`; a plain
`{"allow":true}` works.
