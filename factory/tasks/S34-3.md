Slice: S34 — the kernel never asks a timer past 30 days (`bad-delay`), and a far deadline still fires

## Goal

watane S95 gives the host's `timers.after` a third error, `bad-delay`, for a
delay over 30 days (2 592 000 000 ms). After this task the kernel never asks
such a delay: a session deadline further ahead sets the session timer 30 days
ahead, and that firing, which finds no deadline due, sets the timer again for
the earliest deadline, so a far deadline is still met on time. Today a firing
with no due deadline returns early and re-arms nothing, which would lose the
timer.

**The spec (written by the foreman for S34; quoted, it is the rule):**

2.1: `enum timer-error { too-many, bad-id, bad-delay }     // bad-delay: over 30 days (7)`

7, Timers: "Per mod: ids of at most 128 bytes (else `bad-id`), at most 256
live (else `too-many`), delays up to 30 days (2 592 000 000 ms; a longer one
is refused `bad-delay`, watane S95)".

7, Kernel timers: "The kernel never asks a delay over 30 days, so it never
meets `bad-delay`: a deadline further ahead sets the timer 30 days ahead, and
that firing, which finds no deadline due, sets the timer again for the
earliest one (9.3, "Deadlines and the session timer")."

9.3, Deadlines (existing, unchanged): "When the timer fires, the kernel
handles every due deadline and sets the timer for the next one, or cancels
it; a session whose deadlines are all gone frees its timer." and (as built,
S26) "A firing with no due deadline changes nothing." — this task makes that
last sentence read "A firing with no due deadline changes nothing but the
timer: it sets it again for the earliest deadline (a deadline over 30 days
ahead, 7)."; edit that sentence in `design/TECHNICAL.md` 9.3.

**9.3 "Past" (quoted; this task changes what a firing does):** "The
exceptions cannot fail at the ceiling, since each ends a turn or closes a
session's work and frees what it holds: a firing of the restart pass, a
provider stream's `ended`, `cancel`, `interrupt` without a replacement, and a
provider item while past". A session-timer firing that only re-arms writes
no charged key and changes no count (the session still holds its one timer),
so it cannot fail on quota; it must not write the record or `slots` when
nothing changed.

4.1 `profile` and 12 `bad-delay`: spec text only, already written by the
foreman (no kernel launch builder exists before stage B).

## Acceptance

AC1. A constant `MAX_TIMER_MS: u64 = 2_592_000_000` (doc: 7, `bad-delay`); no
`timer_after` call the kernel makes, through `set_timer` or directly, has a
`delay_ms` over it (one funnel: `set_timer` clamps).
AC2. Crate test (`FakeHost`, `MemState`): a session whose earliest deadline is
40 days ahead (insert a deadline the way the existing deadline tests do; an
`idle` deadline moved in the record, or a test hook the tests already use)
asks `TimerAfter { id: "s/<id>", delay_ms: 2_592_000_000 }`; at day 30 the
firing handles nothing, writes no state key, and asks `TimerAfter` with 10
days; at day 40 the deadline is handled as any due one.
AC3. A firing at a time before any deadline is due (the host fired early)
re-arms for the earliest deadline and changes nothing else (no state write,
`slots.timers` and the owner's `timers` unchanged); a firing for a session
with no deadlines still asks nothing.
AC4. Delays under 30 days are asked unchanged (the existing idle tests pass
untouched).
AC5. TECHNICAL 9.3 sentence edited as above. `cargo test`, `cargo clippy
--all-targets -- -D warnings`, `cargo fmt --check` in `kernel/`, and
`factory/gate.sh` pass.
