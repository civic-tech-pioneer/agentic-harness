## Goal

The overlay half of compilation (TECHNICAL 9.2) and the `check` step that joins it to S3-1's
profile check, plus the `check` example a maker runs: profile, then overlay, then the refuse
table; every refusal printed as one JSON line; nothing started, no host needed. An overlay can
only narrow a profile (AGT-F-3, case 26): this is the slice's guard.

## Acceptance

AC1. `parse_overlay` accepts exactly the keys `system-prompt-append` (text), `skills+` (skills
     as in the profile), `tools-` (tool names), `deny+` (rules), and the limits `max-turns`,
     `max-tool-errors`, `max-tokens`, `max-budget-usd`, `subagent-depth`. Each other key is a
     problem named `overlay.<key>`; a key that widens gets a reason that says so: `tools`,
     `tools+` "adds tools"; `allow`, `allow+` "adds allow rules"; `workspace`,
     `extra-workspaces`, `workspaces+` "adds workspaces"; `subagents`, `subagents+` "adds
     subagent profiles"; `mode` "changes the permission mode"; `system-prompt` "replaces the
     instructions"; anything else "not an overlay field". Not JSON or not an object: one
     problem `overlay`.
AC2. An overlay with `tools+`, `allow+`, `workspaces+`, `subagents+` and `mode: "dont-ask"` on
     a `manual` profile yields from `check` five refusals, one per field, all at once
     (case 26).
AC3. `apply_overlay` appends `system-prompt-append` to the profile's instructions (an existing
     `append` grows; a `replace` keeps replacing, with the text appended to it; none becomes
     `append`), adds `skills+`, removes `tools-` from `tools` and from each subagent's `tools`,
     adds `deny+` to `deny`, and sets each limit. An overlay doing all of these compiles with no
     refusals on `claude`, and the result shows each change.
AC4. A limit in the overlay higher than the profile's is refused naming `overlay.<limit>`
     (reason names both values); equal or lower is accepted; a limit the profile does not set is
     accepted (it narrows). `subagent-depth` compares to the profile's value or its default 1.
AC5. After the overlay, the compiled profile goes through S3-1's `grammar_problems` and
     `refuse`: a `deny+` rule outside the 4.1 grammar is refused, and on `openai` a `skills+`
     skill with a file besides `SKILL.md` is refused (the table sees the compiled profile).
     Duplicate refusals (same field and reason) are reported once.
AC6. `check` returns profile problems, overlay problems and table refusals together, each
     with the backend and model under check; a broken profile still has its overlay checked.
AC7. `cargo run --example check -- p.json o.json openai gpt-5` in `kernel/` prints one line
     `{"field":…,"backend":…,"model":…,"reason":…}` per refusal on stdout and exits 1; with no
     refusal it prints nothing and exits 0; a missing file, an unknown backend or a wrong
     argument count prints a usage line on stderr and exits 2. An optional fifth argument is a
     catalog file (S3-1 `Catalog`, JSON `{"models":[{"slug":…,"efforts":[…]}]}`); without it the
     example writes one note on stderr that model names and efforts were not checked against a
     list. Keep `main` thin; prove the output lines and exit codes at the lowest level that
     shows them (a function of the example's own module is fine), and run the real example
     once by hand, quoting its output in your report.
AC8. `check` starts nothing and reads nothing but its arguments (no files, env or network in
     the library).
