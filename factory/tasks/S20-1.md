## Goal

An ask's card shows what will run. The Claude adapter's `ask` entry carries
an ACP `kind` in its `toolCall`, and for an edit the diff the input
describes, so a real `Edit` ask draws its diff instead of "Other <path>"
(S15 RISK (c)). A second ask or check on a `toolCallId` that already has an
open one with a different `tool` or `input` is an `unknown` entry, never an
ask (S15 RISK (a), failing closed): a client could otherwise draw one card
for two different calls. The spec (9.8) says both, and 9.4's "Code to
change" drops the ten console bullets S15 built.

## Acceptance

AC1. The adapter's ask and check entries (`ClaudeAdapter`, items `ask` and
`check`) put `kind` in `toolCall`, from the item's `tool`: `Read` -> `read`;
`Edit`, `MultiEdit`, `Write`, `NotebookEdit` -> `edit`; `Bash` -> `execute`;
`Grep`, `Glob` -> `search`; `WebFetch`, `WebSearch` -> `fetch`; any other
name (`mcp__...`, `Task`, `ExitPlanMode`, unknown) -> `other`. The values
are ACP v1 `ToolKind` spellings (serialize through
`agent-client-protocol-schema` where it is simple).

AC2. For `Edit` with string `file_path`, `old_string`, `new_string`, the
ask's `toolCall` has `content: [{"type":"diff","path":<file_path>,
"oldText":<old_string>,"newText":<new_string>}]` (ACP v1 `Diff`). For
`Write` with string `file_path` and `content`: one diff with `newText` the
content and no `oldText` (ACP: absent or null means a new file; pick what
the ACP crate writes). For `MultiEdit` with string `file_path` and an
`edits` array of objects with string `old_string`, `new_string`: one diff
per edit, in order. Any of those fields missing or of another type: no
`content`, the ask is still an ask (its `rawInput` and `input` unchanged).
No other tool gets `content`. The diff is built from the item's `input`
only, never from a `ToolCall` of the same id (9.8).

AC3. An `ask` or `check` item whose `tool_use_id` equals that of an ask or
check the adapter still holds open, and whose `tool` or `input` differs
from that open one's (JSON value equality on `input`), is an `unknown`
entry (`raw` the item) and the open one is unchanged. The same `tool` and
`input` on the same `tool_use_id` (a check, then an ask of the same call,
checked mode) is still an ask. Once the open one is resolved
(`ask-resolved` `expired` or `cancelled`, today), a new ask on that
`tool_use_id` with another input is an ask again.

AC4. Tests in `kernel/tests/it/adapters.rs` (and its fixtures) prove AC1-AC3:
one per kind row of AC1 (a table test is fine), Edit / Write / MultiEdit
diffs, a bad-field Edit with no `content`, the conflicting second ask and
check (each `unknown`), the same-call check-then-ask (both asks), and the
re-ask after resolution.

AC5. Spec, `design/TECHNICAL.md`:
- 9.8: after the paragraph "When an ask's input differs ...", say that the
  ask's `toolCall` carries ACP `kind` (the AC1 table, one line) and, for
  `Edit`, `Write` and `MultiEdit`, `content` with the diff(s) of AC2, built
  from the item's `input` only; and add to the "are each an `unknown`
  entry" list: an `ask` or `check` item on a `tool_use_id` that has an open
  ask or check with a different `tool` or `input` (the open one is not
  changed), with the reason (one card per call: a client draws the card of
  a call from its ask, 18.3).
- 9.4 "Code to change.": remove the ten "Console, a console slice after S9"
  bullets (S15 built them) and the "**Code to change.** The wire above
  differs ..." lead line with them, since nothing is left under it. Keep
  "**Code to change (S20).**" and "(a later slice)" as they are (S20-2 and
  S20-3 edit those).
- 16: a case 75 for AC1-AC3 (kernel crate, adapter): an `Edit` ask's
  `toolCall` has `kind: edit` and its diff; a second ask on the same call
  with another input is `unknown`.
