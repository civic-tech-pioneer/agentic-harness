## Goal

The kernel reads the host's generation through `host-info.generation()`
instead of `caller.boot()`, in code and in every spec mention, and the
contract records the human's acceptance of the three host-wire additions.
After this task `grep -rn "caller.boot\|caller\.boot\|fn boot\b\|HostCall::Boot"
design/TECHNICAL.md design/FUNCTIONAL.md kernel/` finds nothing (except the
quoted words of the human in TECHNICAL 2.1 G1, "in place of `caller.boot()`").

**The rule (the human, 2026-11-21, quoted; it is the rule):** "(1) the three
host-wire additions are accepted, with restart detection as a new interface
`host-info` with `generation()` (in place of `caller.boot()`); `outcome` on
`answered` and checks closed by the host with `expired` as written."

**Already in the spec (TECHNICAL 2.1, written by the foreman):**

> interface host-info {                                // no grant (the human, 2026-11-21)
>   generation: func() -> u64;  // the host's start number (rule G1)
> }

> **G1.** `host-info.generation()` is the host's generation, its start number:
> raised once each time the host starts, kept in host state, the same for every
> call until the next start. It is a pure read: not a request (below), no grant.
> [...] The kernel's stored fields that hold it keep the name `boot`:
> `slots.boot`, a record's `boot`, the `active/` pair and the `slots/wait/`
> entry; each holds a generation.)

So: stored field names and the on-disk format do not change. The host's
function, the kernel's trait method and the prose that names the host's call
do. "Boot number" in prose that means the host's value becomes "generation"
(e.g. "the boot number of the call that queued it" -> "the generation of the
call that queued it"); a stored field keeps its name `boot`.
