## Interface

Fixed. These are the rules to write.

**P01 (9.4).** An entry is at most 256 KiB serialized. A larger one is stored, read and pushed
as consecutive `part` entries:
`{"v":1,"i":<k>,"kind":"part","at":…,"body":{"n":<1..m>,"m":<m>,"text":"<slice>"}}`.
`text` is a slice of the whole entry's serialization, cut at UTF-8 character boundaries; the
whole entry carries the index of its last part. A reader joins the `text` of parts 1..m in
order and parses the result as one entry. `attach` and `read` with an `after` that falls inside
a group start at the group's first part. Live, a finished entry over 256 KiB goes out as its
parts, as replay pushes entries, never as one update. So every chunk (1 MiB), `read` page
(2 MiB) and replay (2 MiB) holds at least one whole entry or part, and paging always makes
progress. No content is cut by this rule (tool output stays cut at 64 KiB, as before).

**P02 (9.1, 9.3, 2.3, 12).** Every input (`start`, `say`, an `interrupt` replacement) is at
most 256 KiB serialized, else `too-large(262144)`. The queue lives in its own key `queue/<id>`
(not in the record): at most 32 inputs and 2 MiB in all; past either, `queue-full`. The `queue`
update and `queued` therefore stay under 2 MiB. The session record is at most 512 KiB; its
variable fields:

| Field | Cap | Past it |
|---|---|---|
| `key` (a client key, also in `key/<owner>/<key>`) | 256 bytes | `too-large` |
| `title` | 256 bytes | `rename` refuses `too-large` |
| `children` | live children only, at most 20 (9.7); a finished child leaves the list, its id stays in the parent's transcript | – |
| `allows` | 64 session allows of at most 1 KiB each | an answer `for: session` is refused `too-large`; the ask stays open |
| `chunks` | 16 384 chunk starts | the session is at its quota: the turn ends `stopped {quota}` and new input is refused `quota` |

`error` in 2.3 gains `too-large(u64)` (the limit in bytes). AGT-F-11 and AGT-F-54 change (below).

**P03 (2.1, 3, 9.4, 10, 12, 15).**
```wit
enum sink-outcome { taken, defer }
interface stream-sink { items: func(s: string, items: list<item>) -> sink-outcome; ended: func(s: string, outcome: outcome); }
// in interface streams:
resume: func(s: stream-id) -> result<_, stream-error>;   // consumer only
```
Section 3 rows:
- **Deferred batch:** an `items` call that returns `defer` is rolled back like a failed call
  (its pushes and writes are dropped) but is not a failure: it does not count towards
  `consumer-failed`. The host keeps that batch and every later item, delivers nothing more on
  that stream, and a host stream stops reading its source, until the consumer calls `resume`.
- **Resume:** consumer only; the host then delivers the kept batch again, with the same
  numbers. `resume` of a stream that is not deferred does nothing.

A forwarding mod defers when a `push` to its own downstream stream fails `full`, and resumes in
its `stream-producer.ready` for that downstream stream. The checked provider (10) and the
kernel (for its owner's live stream) both do so. Outside an item call (a `say`, an `answer`, a
timer), the kernel cannot defer: if a push to the owner's live stream fails `full`, it closes
that stream with outcome `lagging`, and the client attaches again after its last index (9.4).
`lagging` joins the stream outcomes of 12.

**P04 and outcome 5 (4.5, 10, 15).** The host pushes an item `{"type":"initialized"}` on a
`claude-code.start` (and `claude-code-shell.start`) stream once 4.5 step 2 has passed. The host
starts the process only after the workspace consent is held (8), so `initialized` never comes
before it. The checked provider's `start`:
1. checks the caller (2.2), checks the launch's form, opens its own stream to the kernel, calls
   `claude-code.start` with `pre-tool-check` and **no input**, stores
   `pending/<own stream> {launch, input}` in its state, and returns `{stream: <its own>,
   direct: false}` in the same call. It forwards `consent-pending` and every other item.
2. On `initialized` (an item call), it starts the judge call for the launch and the input.
   Nothing of the session goes to the judge before that item (outcome 5; deputy decision of
   2026-11-20 on S2's RISK 3).
3. Every judge call spans calls: `https-stream.start` (a request, 7), a timer
   `judge/<on>` at the deadline (`timeout-s` minus 2 s), the verdict read from the judge
   stream's items. At most 3 attempts, each started from the `ended` of the one before, only
   while the deadline is ahead. The timer firing first is `unsafe`; a later verdict is ignored.
4. Safe on the launch and input: `claude-session.say(input)`. Unsafe: a verdict item, then it
   cancels the `claude` stream and closes its own; the kernel ends the turn
   `idle {failed {judge}}` with the verdict's reasons.
5. `say` from the kernel is judged the same way (steps 3–4), one input at a time in order; it
   returns at once, and the input reaches `claude` only after its safe verdict.
6. `ask` and `check` items are judged the same way and answered by `claude-session.answer`
   after the verdict or at the deadline (`deny`). Claude's own hook timeout (`timeout-s`,
   `onFailure: block`) still stops the tool if the provider never answers.
No call of the provider waits for the judge, so no call nears its budget.

**P05 (9.1, 9.5).** The kernel consumes at most 32 streams (3). It splits them: 8 provider
streams (Claude sessions; the host's limit of 8 `claude`), 8 model requests
(`https-stream.start` of the OpenAI loop), 16 tool jobs; one session holds at most 8 job slots.
State: `slots` → `{provider, request, job: counts; head, tail}`, and `slots/wait/<n>` → a
session id waiting for a slot (a FIFO). The loop state keeps a step's calls not yet started
(`pending`); they start in waves as job slots free. A request that finds no request slot waits
in `ready` in the FIFO. Every `ended` of a kernel-consumed stream frees its slot and starts the
oldest waiting work in the same call. The restart pass that writes `unknown` (9.3) sets the
counts to zero (streams are memory only, 3). The "Parallel" rule becomes: the jobs of a step
start together, up to the free job slots, only when every tool is `parallel`; else one after
another, in call order.

**P06 (9.5, 16).** Case 2 becomes: "Each request of an ordinary step extends the previous one
without moving its prefix (cache). Trimming by the body budget, a compaction and a summary
restart each start a new prefix, once; the request after it extends that one. `instructions`
are byte-stable through all of them." (three tests: one per kind of new prefix).

**P13 (2.3, 9.4, 18.3).**
```wit
read: func(session: string, after: u64, before: option<u64>, max: u32) -> result<page, error>;
record page { entries: list<string>, last: u64 }
```
Without `before`: the oldest entries with `i > after`. With `before = b`: the newest entries
with `after < i < b`. Both: in ascending order, at most `max` (at most 256) and 2 MiB. `last`
is the session's highest stored index when the call ran (the high-water mark), so a client
paging backwards knows where the live end is. 18.3: "page with `read` backwards (`before`),
newest page first".
