## Goal
An OpenAI session's tool calls run through the kernel's tools: the profile's `toolsets` are opened
on `agent-tools` at the session's first request, described into the request's `tools`, each call of a
response is decided by the broker (the profile's deny, ask and allow rules; an ask goes to the owner
as a Claude ask does), allowed calls run as jobs within the job slots, and every call gets exactly
one output before the next request. After a restart, idempotent jobs run again under their keys and
the others are `aborted`.

## Acceptance
AC1 A profile with `toolsets: ["notes"]`: the first request is preceded by `ToolsOpen {["notes"]}` and `ToolsDescribe {h1}` (the handle kept in the record's `handle`); the body's `tools` is one `{"type":"function","name":<name>,"description":<d>,"parameters":<input-schema as JSON>,"strict":false}` per tool, in the order described, the same bytes in every later request of the session. A profile with no toolsets opens nothing and sends no `tools`. `tools_open` answering `consent-pending(<what>)` sets the turn's activity `consent {what}` and retries the open with the retry backoff of 9.5; `consent-refused(<what>)` or `not-granted` ends the turn `idle {failed {error: <that text>}}`.
AC2 Broker (9.6): with `allow: ["notes_*"]` a call runs at once; with `deny: [...]` matching, the call gets the output `{"error":"denied by the profile"}` and runs nothing; a call no rule names in mode `manual` (or with an `ask` rule) opens an ask entry for the owner (kind `ask`, the call's `call_id` as `toolCallId`, its parsed `arguments` as `input`, `expires-at` = now + `ask-expiry` seconds, 600 when the profile sets none) and the turn is `waiting {asks}` with an `ask <id>` deadline; in mode `dont-ask` it is denied. No live owner stream, or an owner `agent:...`: denied at once (9.6). An ask with `ask-expiry: 0` is denied at once, reason `expired`.
AC3 `answer` on an OpenAI ask: `{"allow":true}` runs the call; `{"deny":true,"reason":"r"}` gives the output `{"error":"denied: r"}`; `{"allow":true,"for":"session"}` is refused `{field: "decision"}` (an OpenAI ask has no `reach`: tools of a toolset have no scope function, 9.6); a second answer is refused as for Claude (case 9); the ask's deadline firing denies it, reason `expired`. When every ask of the step is decided the allowed jobs start.
AC4 Jobs (6): each allowed call is `tools_call(handle, "<session>/<call_id>", name, arguments)`; its stream's `stream/<id>` kind is `job`; its one item `{"ok":v}` becomes the output `v` as JSON text, `{"err":{code,message}}` the output `{"error":"<code>: <message>"}`; a job stream that ends with no item gives `aborted`; each output is stored in the wire and shown to the owner as the Responses adapter maps a job output (the tool call entry completes or fails). When all of a step's calls have outputs the loop is `ready` and sends the next request. The turn's `tools` counts the calls.
AC5 (case 39) A response with 33 parallel calls of tools that are all `parallel`: at most 16 jobs kernel-wide and at most 8 of one session are open at once (count `ToolsCall` against job `ended`s); the rest wait in the loop state's `pending` and start in waves as slots free, in call order; every call gets exactly one output; while they run, another session's model request still starts; when one tool is not `parallel`, the calls run one after another in call order.
AC6 (case 48, job part) One owner holds at most 8 job slots; another owner's jobs still start.
AC7 (case 22) Restart (R4) with a loop in `tools`: open jobs of `idempotent` tools are called again under the same keys; the others get `aborted`; `pending` calls start in waves; with nothing open or pending it goes `ready`. *(Narrowed in review r2 by the deputy, 2026-11-24: every open job, idempotent ones included, and every `pending` call gets `aborted` with no `agent-tools` call, and the loop goes `ready`; reissue under the key is Upkeep. Cut in review r3, 2026-11-25: the turn then becomes `unknown` and sends no request; the owner's next `say` continues it.)* `waiting` is unchanged *(review r4, F4.1: a `waiting` turn stops `unknown` too, its asks denied `by: kernel`, reason `restart`, its calls `aborted`)*. Slot counts start from zero after the restart (case 39's last part).
AC8 `interrupt` and `cancel` while `tools` or `waiting`: every job stream is cancelled, every open call gets `aborted`, every open ask is denied `by: kernel`, job slots are freed in that call, the turn ends `idle {interrupted}`; `cancel` and `delete` also `tools_close` the handle.

AC9 A response's calls are the `function_call` items of its output: dev's scripted server (and a stream that omits `response.output`) sends them only as `response.output_item.done` events, so the loop keeps each `Sse::Item` of the response (in the loop state, written with the batch that took it) and, at `Sse::Completed`, uses `output` when it is not empty and else the kept items, both for the wire and for the calls. A test feeds dev 18.3's literal `ToolCalls(3)` events then `Completed` and sees three calls run.
AC10 A job item, or a decided ask, that leaves the loop `ready` inside an items call queues the next request with the loop's FIFO helper (`enqueue`, S40-3) and lets the call's end send it; it never calls `https_start` directly inside an items call (it may still be dropped, `Defer`). *(Review r5, F5.1: that call's end sends it or stops the turn `busy`; the items and end of a job the FIFO started send no model request.)*
