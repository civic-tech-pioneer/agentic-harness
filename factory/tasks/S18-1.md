## Goal

The spec says what the kernel does with every odd host item, so a maker of stage B's host part and
a kernel maker read the same rules the code holds. TECHNICAL 4.5 lists the values of
`ask-resolved`'s `by`. 9.4 and 9.8 state what S14 built ahead of the spec and what S19 builds
(PO decision, `factory/PLAN.md` Deputy decisions 2026-11-21 "S14's open points"). Section 14
"Not protected" names the two accepted limits. FUNCTIONAL AGT-F-10 says "never as running when
nothing drives it", which matches TECHNICAL 9.3 R4.

The sources are PR #18's body (S14's "Decisions" and "For the PO" points 1 to 6), PR #20's body
(S17's "For the PO" point 2), and the S19 briefs on `origin/slice/S19`
(`factory/tasks/S19-1.md`, `S19-2.md`). They are quoted where needed below. Do not read them as rules.

**Foreman's decision (`by` values).** Step 5 of 4.5 already promises an `ask-resolved` after any
answer, so the host sends three values:
- `answered`: after an `answer` the host accepted, whoever called it;
- `expired`: the host's own deny at `expires-at`;
- `cancelled`: `control_cancel_request`.

The kernel reads them like this:
- `expired` or `cancelled` on an open ask or check gives the decision entry `by: host`,
  `reason` = the `by`, as today;
- `answered` closes the open ask or check and writes no entry: the call that answered wrote its
  decision (9.4, 9.6);
- any other `by`, a missing `by`, or a `by` that is not a string gives an `unknown` entry, and the
  ask stays open (S19).

S19 builds the "any other" rule now and treats `answered` as unknown too. So 9.4 lists one item for
a later kernel slice: `answered` closes the ask with no entry. How a check answered by the checked
provider becomes a `by: checked` decision stays with stage E (10). Do not design it here.

## Acceptance

AC1. TECHNICAL 4.5 lists the `by` values `answered`, `expired` and `cancelled`, and says when the
     host pushes each:

     - step 5's sentence "After any answer, and when an ask expires … pushes `ask-resolved {id, by}`"
       names `answered` for an answer and `expired` for the expiry;

     `grep -n '"answered"\|`answered`' design/TECHNICAL.md` finds 4.5 and 9.8.
AC2. TECHNICAL 9.8, in the paragraph that starts "Give nothing" and in the `ask`, `check`,
     `ask-resolved` row, states each of these. An item that breaks a rule is an `unknown` entry,
     never an ask or a decision.
     1. The `id` of `ask`, `check` and `ask-resolved` is a non-empty JSON string. A number or
        another JSON value is `unknown` (S14). So `"7"` and `7` never name the same ask.
     2. `input` of an `ask` or `check` is a JSON object. Missing, `null` and any other JSON value
        are `unknown`; `{}` is an object (S19).
     3. `expires-at` is a JSON integer from 0 to 2^64 − 1. A negative or fractional value, `5.0`,
        `1e3`, a value past 2^64 − 1, a string and `null` are `unknown` (S19). This replaces "is
        not a number".
     4. `ask-resolved` follows the `by` rules of the Goal: `expired`/`cancelled` give a decision;
        `answered` closes the ask with no entry; any other or missing `by` is `unknown` and the ask
        stays open, so a later `expired` or `cancelled` still gives its decision (S19). An
        `ask-resolved` whose `id` is not open is `unknown`.
     5. Strict reading. A line that is not valid UTF-8 is `unknown`. Its `raw` is the line as a
        JSON string: each byte that is not UTF-8 is written as the four characters `\xNN`
        (lowercase hex), and white space is trimmed from both ends. A literal `\xff` in valid text
        reads the same: an accepted ambiguity, only for display. There is no lossy decoding. The
        host's `wrapped` `line` (4.5) keeps U+FFFD. That is the host's form, not a conflict:
        say so in one clause.
     6. A line with a key twice at its top level is `unknown` in the kernel too, the kernel's half
        of 4.5's "never read one line two ways". Keys below the top level are read last-wins
        (see AC5).
AC3. TECHNICAL 9.4, parts, says a joined part group reads as `read` reads a stored line at its
     last part's place:
     - it takes that place's `i`, and any `i` in the joined text is ignored (S14);

     - a joined whole of kind `part` is `unreadable` (S19);
     - a stored `part` line, read alone, is still a `part`.
