## Goal

An OpenAI root delegates to named OpenAI profiles (sketch outcomes 1, 2, 4; AGT-J5). The root's
requests advertise `task(profile, input)`; a `task` call is admitted (9.7, all five steps), starts a
child session (owner the root's, `parent` the root, no workspace) whose first turn runs the input,
writes one indexed `child` entry in the root's transcript, and resolves the call with exactly one
terminal output when the child's first turn ends. Revoked access refuses `task` with `profile`.
This task decides, inside the spec, where the pending association lives in state and how a child's
first request is started inside an items call (the FIFO rule of 9.5): name both in a doc comment of
`kernel/src/openai/task.rs`, and keep both within the one-call bound (17).

## Acceptance

AC1. A root profile with `delegates: ["foreman","validator"]`: its request body's `tools` ends with
     the `task` definition (name `task`, parameters object with required string `profile` and
     `input`, no other properties); a root with no delegates, a child, and a `summary` request (S134-2)
     send no `task`.
AC2. Two `task` calls in one response (parallel) for the two names -> two child records (owner =
     root owner, `parent` = root id, backend `openai`, no `workspace`, `handle` or folder), the root
     record's `children` lists both, two `child` entries `{"session","toolCallId"}` in the root's
     transcript (pushed live, replayed on attach), each child's first turn running with the call's
     `input` as its user message, and the root `tools`/waiting with both calls open (a `child
     {session}` call state, 9.5 Calls). The child's id is readable by the owner via `read`/`attach`
     the moment the `child` entry is committed.
AC3. A child that completes with text T -> the root's call output is exactly
     `{"ok":{"session":"<id>","message":"T"}}` (stored in the wire, shown as the tool entry); when
     both outputs are in, the root's follow-up request is sent (under 9.5's origin and slot rules)
     and its final answer completes the root's turn. Text over 64 KiB is cut inside `message` and
     the envelope stays valid JSON.
AC4. Child endings -> `{"err":{"code":C,"session":"<id>"}}` with C = `max-turns` /
     `max-tool-errors` / `max-tokens` / `busy` (a limit stop), `backend` (failed), `no-result`
     (completed with no text), `interrupted` (the owner interrupts the child's first turn). A
     second turn of the child (owner `say`) never writes a root output.
AC5. Refused dispatch -> output `{"err":{"code":"refused","refusals":[…]}}` with the 2.3 records,
     no child record, no `child` entry, no id taken: a name outside `delegates` (`profile`), a
     missing profile (`profile`), a third call at `subagent-limits.live: 2` with two live
     (`subagent-limits.live`), a widening candidate (its field), a `task` call emitted by a child
     (`subagent-limits.depth`).
AC6. Revoking (9.7): after `access/<owner>` stops naming the root's profile, a `task` call gets the
     `profile` refusal as its output and the turn goes on; `read`, `attach`, `list` of root and child
     still work; a `say` on the child is refused `profile` (the root's profile is checked, against
     the root's owner); a child whose root record is missing is refused `profile` for `say`.
AC7. Busy: a `task` dispatched in a call that may be another owner's (a drained job's item), or at
     a busy cap before start -> output `{"err":{"code":"busy"}}`, no child. A waiting `task` holds
     no request or job slot; the child's own request and jobs count against the root owner's caps
     (case 52, `task` part); resolution removes the association once.
AC8. The broker's rules for the name `task` apply first: a deny rule `task` -> the profile denial
     output, no child; mode `manual` with no allow rule for `task` -> an ask, and the child starts
     only after the owner allows it.
AC9. A toolset whose `describe` lists a function named `task` or `skill` -> the turn fails before
     any request with an error naming `toolsets` (9.7).
AC10. A `child` entry kind exists in the transcript format (9.4) and in `wire_update`/push shape the
     console reads: `{"kind":"child","body":{"session":"<id>","toolCallId":"<call id>"}}`.

## Interface

Takes: `delegation::admit` and `live_cap` (S134-3); `LoopState.summary`, `Policy` limits and the
streak counting in `put_output` (S134-2).
Provides (fixed; S134-6 and S134-5 use them):
- `CallState::Child { session: String }` in `kernel/src/openai/tools.rs`.
- `Record.task_call: Option<String>` (serde `task-call`, skipped when none): on a child, the root's
  call id while its delegated first turn is outstanding; cleared when that call is resolved.
- `pub(crate) fn resolve_task(&mut self, child: &mut Record, output: String, ok: bool, cx: &mut Cx)`
  in `kernel/src/openai/task.rs`: writes the root's output once and continues the root as
  `after_output` does; a no-op when the root no longer has a `Child {session}` call for this child.
- The `child` entry as AC10.
