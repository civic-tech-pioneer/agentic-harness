## Goal

A Claude ask or check gets exactly one decision entry, written when it
closes, as 9.8 rule 4 says. The owner's `answer` is kept as a pending
answer in the session record and becomes the entry when the host's
`ask-resolved` arrives; `answered` closes with the pending answer or the
host's / checked provider's `outcome`; `expired` and `cancelled` close with
`deny, by: host`; the provider stream's `ended` and the restart step (in
every turn state) close every open or pending ask. A session holds at most
64 asks and checks without a decision entry; one past that is denied at
once (`busy`), so no closing call writes more than 64 decisions. Case 73
proves it. Guard: this is the asks boundary of 14 ("An ask shows the tool
call that will run").

## Acceptance

AC1. **Pending answer.** `Record` gains `pending-answers` (serde name), a map
ask id -> `{i, kind, outcome, by, for?, reason?}` (`i` the index of the ask
entry, `kind` `ask` or `check`, so the decision can repeat the ask after a
restart without the adapter; `outcome` `allow`/`deny`). The owner's
`answer` to an open Claude ask writes **no** entry: it moves the ask from
`open` to `pending-answers` (`by: owner`, `for: session` when given,
`reason` when given), adds the session allow when `for: session` as today,
updates the turn as `close_ask` does today, and sends `Request::Answer`
as today. A pending answer over 1 KiB serialized refuses the answer
`too-large(1024)` and writes nothing. A second `answer` to it is refused
`{field: "ask"}` (case 9). With 64 pending answers the `answer` is refused
`busy` (its message names the cap) and writes nothing. An OpenAI session's
answers are out of scope (no OpenAI loop yet): change only the Claude path,
and if the code has no backend switch there, answer every session the
Claude way.

AC2. **The adapter reports, the kernel decides.** `ClaudeAdapter::resolved`
no longer builds a decision entry. It checks the item's shape and returns an
`Out` with `resolved: Some(Resolved {..})` and no entry, or an `unknown`
entry:
- `id` a non-empty string, else `unknown`;
- `by` a string, one of `answered`, `expired`, `cancelled`, else `unknown`;
- `answered`: `outcome` a string, one of `allow`, `deny`, `none`, else
  `unknown`; `none` on an ask or `allow` on a check (the kind from the
  adapter's `open` map) is `unknown`;
- `expired` / `cancelled` carrying an `outcome` key (any value) is `unknown`;
- an `id` not in the adapter's `open` map is `unknown`.
On a `Resolved` it removes the id from its `open` map; on `unknown` it
keeps it. `ClaudeAdapter::new()` is a `direct: true` stream;
`ClaudeAdapter::checked()` a `direct: false` one (the checked provider's,
10); `Resolved.direct` carries it.

AC3. **Closing at `ask-resolved`.** `Kernel::provider` with an `Out` whose
`resolved` is set: the id must be in the record's `open` or
`pending-answers`, else one `unknown` entry with `raw` the item, and
nothing else changes. Kind rules again from the record (`none` on an ask,
`allow` on a check: `unknown`, the ask as it was). Otherwise exactly one
decision entry: the ask body read at its `i` (as `ask_body` does) plus
`decision`:
- `answered` with a pending answer of the same `outcome`: the pending
  answer (`outcome`, `by`, `for`, `reason`);
- `answered` otherwise: `{outcome, by: "checked"}` when `direct` is false,
  else `{outcome, by: "host"}`, no `reason`;
- `expired` / `cancelled`: `{outcome: "deny", by: "host", reason: <by>}`.
The id leaves `open` (the turn follows as `close_ask` does) or
`pending-answers`. A session allow the pending answer added stays.

AC4. **The cap of 64.** An `ask` or `check` entry from the provider when
`open.len() + pending-answers.len()` is already 64: the ask entry is
appended, then at once its decision entry
`{outcome: "deny", by: "kernel", reason: "busy"}`; it never enters `open`,
the turn does not change for it, and the kernel sends
`Request::Answer {decision: {"deny":true,"reason":"busy"}}` for it. A later
`ask-resolved` of it is `unknown` (AC3). So `open` + `pending-answers`
never pass 64.

AC5. **The stream's `ended`.** `ProviderEvent::Ended` (new variant): in that
one call every pending answer becomes its decision entry (as AC3's first
row) and every open ask or check gets `{outcome: "deny", by: "kernel",
reason: "ended"}`; `open` and `pending-answers` end empty; the turn follows
as `close_ask` does. Nothing else changes in this task.

AC6. **The restart step in every state.** R4 (`step`) closes every open ask
or check (`deny, by: kernel, reason: restart`, its `ask` deadline dropped)
and every pending answer (its decision) whatever the turn state and
backend's state, not only Claude `running` / `waiting`; the turn rows of R4
are otherwise unchanged (`idle`, `unknown`, `resume-lost`, `paused` keep
their turn). One shared helper writes these closing decisions for AC5, AC6
and S20-3's `cancel` (Interface).

AC7. Case 73 as `kernel/tests/it/asks.rs` (new module, in `main.rs`): (a) to
(f) of case 73 and (g) for the restart step (S20-3 adds `cancel` to (g));
each asserts exactly one decision entry per ask id over the whole
transcript. Plus: the cap (65th ask denied `busy` at once, one decision, a
`Request::Answer`; then `ended` writes 64 decisions); the 1 KiB and 64
`busy` refusals of `answer` writing nothing; an unknown or bad
`ask-resolved` leaving the ask open so a later `expired` closes it; a
`checked()` stream's differing `answered` giving `by: checked`.
