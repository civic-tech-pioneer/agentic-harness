## Goal

TECHNICAL.md says, for every order of host items and kernel calls, when the one decision entry of
a Claude ask or check is written and what it says. The sources are S18's adversary RISKs (PR #22's
body, "For the PO" 1–4), quoted in `factory/PLAN.md` "### S22". Do not read them as rules; the
foreman's decisions below are the rules to write. Each fails closed today: only the record can be
wrong, never a tool that runs.

**Foreman's decisions.**

D1 (RISK 1, when the decision is written). A Claude ask's decision entry is written **once, when
the ask closes**, never at the kernel's `answer`. When the kernel answers a Claude ask itself (the
owner's `answer`, a session allow, the "no owner stream" deny of 9.6), it keeps that answer as the
ask's **pending answer** (`{outcome, by, for?, reason?}`, in the session's state so it survives a
restart) and writes no entry. While an ask has a pending answer it counts as decided, exactly as
9.8 rule 4 says today (a second `answer` refused `{field: "ask"}`, no session allow, `ask-expiry`
or restart step answers it again, not counted as open for the owner). It closes:
- at `ask-resolved {by: answered, outcome}`: when `outcome` equals the pending answer's outcome,
  the decision entry is the pending answer (its `by`, `for`, `reason`); when it differs, the
  decision entry has the item's `outcome`, `by: checked` on a `direct: false` stream and `host`
  otherwise, no `reason`, and the pending answer is dropped. (A session allow the pending answer
  added stays; a later matching ask is still judged by the checked provider, 10.) Example: checked
  mode, the owner's allow while the verdict is pending, then an unsafe verdict: the provider
  denies, the host pushes `answered`/`deny`, and the one decision is `deny, by: checked`.
- at `ask-resolved {by: expired|cancelled}`: the decision `deny, by: host, reason` = the `by`; the
  pending answer is dropped (the host denied or `claude` cancelled; what the kernel sent never
  took effect).
- at the kernel's own closing steps (`cancel` 9.3, the restart step R4, and the provider stream's
  `ended`, D5): the decision entry is the pending answer (it is what the kernel sent).
An ask or check with no pending answer that the host closes with `answered` gives the decision
entry from `outcome` as today (`by: checked` / `host`). A kernel ask (OpenAI) is unchanged: its
decision is written at its answer.

D2 (RISK 2). Follows from D1: an `expired` or `cancelled` on an ask with a pending answer gives the
one decision above, never a second one. An `expired` or `cancelled` item that carries an
`outcome` key is `unknown` (the ask stays as it was, open or pending).

D3 (RISK 3). A checked provider, a trusted holder that forwards every host item, can push its own
`ask-resolved` or a false `outcome`. No rule can tell its item from the host's on a `direct: false`
stream. Name it in 14 "Not protected": the record then shows a decision `claude` did not get, or
closes an ask the host still holds (the host denies it at its `expires-at`); no tool runs because
of it, since the kernel's answers reach `claude` only through that provider, which may deny any
call anyway (10).

D4 (RISK 4, a check whose hook times out). The host closes checks too: at a check's `expires-at`
(push time plus `timeout-s`, 4.5) the host pushes `ask-resolved {by: expired}` for a check it has
not answered and writes nothing to stdin for it (`claude`'s own hook timeout, `onFailure: block`,
already blocks the tool). A later `answer` to it is `unknown-ask`. 9.8 rule 4 already gives
`expired` on a check its decision (`deny, by: host, reason: expired`). Accepted gap, named in 14
"Not protected": `claude` starts its hook timer when it writes the line, a little before the host
pushes the item, so an answer that lands in that gap is recorded (`answered`, `none`) while
`claude` already blocked the tool; the checked provider answers 2 s before its deadline (10), so
only a stuck provider reaches it. The host change joins the H2 checklist line in 15.

D5 (an order no item covers). When the session's provider stream ends (its `ended`, 3) while an ask
or check is open or pending, the kernel closes each in the same call: a pending answer becomes the
decision (D1); an open one gets `deny, by: kernel, reason: ended`. So no Claude ask stays without a
decision. `ended` joins the `kernel` reasons listed in 9.4.
