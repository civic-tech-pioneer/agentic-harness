## Goal

The kernel answers Claude asks itself where 9.6 says so. When a new Claude
ask is stored: if its `reach` equals a held session allow's and the owner may
still use the session's profile (`access/` read again, PO decision S20), the
kernel answers `allow`, `by: session-allow`, as a pending answer; otherwise,
when the owner is an `agent:` identity or has no attached owner stream, the
kernel answers `deny`, `by: kernel`, reason `no-owner`, as a pending answer;
otherwise the ask goes to the owner as today. A revoked profile makes a
matching ask go to the owner instead (fail closed). After `take-back` the
same call asks again.

Spec (quoted):
- 9.6: "An ask goes to the owner when it has an attached stream; otherwise,
  and for an `agent:` owner, it is denied." "For Claude, rules went in as
  flags; the broker sees only asks. The kernel's own answer to a Claude ask
  (the owner's, a session allow, the "no owner stream" deny above) is kept as
  a pending answer; its decision entry is written when the ask closes (9.8
  rule 4). A session holds at most 64 open asks and checks with the pending
  answers counted in (9.3); an ask past that is denied at once, `by: kernel`,
  reason `busy`." "Later asks that match an allow are answered `allow` by
  the kernel, with `by: session-allow`. `take-back` removes the allow,
  writes an `allow` entry, and later matching calls ask again."
- PLAN, deputy decision S20: "a `for: session` allow given before `access/`
  is revoked must not keep allowing calls: the slice that builds
  session-allow matching (the broker, 9.6) reads `access/` before answering
  from a session allow, failing closed."
- 9.3 `pending-answers` cap: "the kernel sends no further answer to a Claude
  ask of the session until one closes: (...) a session allow or the "no
  owner stream" deny leaves the ask open for the host to close at its
  `expires-at` (4.5)".
- 9.8 rule 4: "While an ask has a pending answer it counts as decided: a
  second `answer` is refused `{field: "ask"}` (case 9), no session allow or
  restart step answers it again, and it is not counted as open for the
  owner."
- 9.3 "Past" (this task changes what a provider item writes; hold to it):
  "*Any call when past* (the owner or the account; a provider item, ...): an
  ask decision and the host's `ask-resolved` are stored (short, 9.4); (...)
  a new ask is not stored and is denied at once (`Request::Answer` deny,
  reason `quota`); any other entry is not stored." So past quota nothing of
  this task runs: the new ask is not stored and is denied `quota` as today.

Decisions the foreman made (build them as written):
- An ask matches an allow when the `reach` the kernel stored on the ask
  (S31-2's `broker::reach`) equals the allow's `reach`, byte for byte. No
  other matching (so `Bash` holds only its exact command).
- Order for a new, stored, undecided Claude ask of kind `ask` (after the
  64-cap `busy` check, which stays first): (1) a matching allow and
  `may_use(owner, profile)` -> pending `{outcome: allow, by: session-allow}`
  (no `for`, no `reason`), `Request::Answer {"allow":true}`; (2) else an
  owner starting `agent:` or `rec.live` is `None` -> pending
  `{outcome: deny, by: kernel, reason: "no-owner"}`,
  `Request::Answer {"deny":true,"reason":"no-owner"}`; (3) else open, as
  today. In (1) and (2) the ask never enters `open` and the turn does not go
  to `waiting` for it (no `waiting` push for it); when the pending answers
  are at 64, it is opened as in (3) instead and the kernel sends nothing.
- A `check` is never answered by (1) or (2): only the checked provider
  answers a check (2.3, 10).
- The decision entry comes when the host's `ask-resolved` closes the ask,
  as for any pending answer (9.8 rule 4): `answered`/`allow` gives
  `{"outcome":"allow","by":"session-allow"}`; `expired` gives `deny, by:
  host`.

## Acceptance

AC1 (case 28). With an owner stream attached, a `Bash` ask `npm test`
answered `{allow, for: session}`; then a second `Bash` ask `npm test`
(another id and call): the host gets `Request::Answer` `{"allow":true}` for
it at once, the record's `pending-answers` has it with `by: session-allow`,
it is not in `open`, the turn stays `running`; its `ask-resolved`
`answered`/`allow` writes one decision `{"outcome":"allow","by":"session-allow"}`.
No request the kernel sends carries `for` or `updatedPermissions`.

AC2. A third ask `npm test --watch` (another command) or `Bash` `ls`, and a
`Write` ask after an `Edit(/w/**)` allow, go to the owner (open, `waiting`).

AC3. After `take_back` of the allow, the same `npm test` ask goes to the
owner (open, `waiting`), no `Request::Answer` sent.

AC4. Revoked (S20): with the allow held, `access/alice` rewritten to `[]`
(and, separately, to an unreadable value `{}`), a matching ask is not
answered from the allow: with an owner stream it is open (`waiting`);
without one it is denied `no-owner`. Restoring `access/` makes the next
matching ask allowed again.

AC5. No owner stream: with none attached (never attached, or after the
stream's end clears `live`), an ask is answered pending
`{outcome: deny, by: kernel, reason: "no-owner"}`, `Request::Answer`
`{"deny":true,"reason":"no-owner"}`, the turn does not go `waiting`; its
`ask-resolved` writes the decision `deny, by: kernel, reason: no-owner`.
An owner `agent:x` with a stream attached: the same deny.

AC6. A `check` with no owner stream stays open (the checked provider's).

AC7. The 64 cap: with 63 open asks and checks plus pending answers, a
matching ask is answered from the allow (it becomes the 64th pending/open);
at 64, a new ask is denied `busy` at once (unchanged). With 64 pending
answers held and 0 open, a new ask is denied `busy` too (the cap counts
pending). (If the cap makes "pending full but room to open" unreachable,
say so in a test comment and test the branch with a unit test instead.)

AC8. Past quota: a matching ask is not stored and is denied `quota` (as
today), no `session-allow` pending answer.

AC9. `cargo test`, `cargo clippy --all-targets -- -D warnings`,
`cargo fmt --check` and `factory/gate.sh` pass.

## Changed tests

Every existing test that feeds a Claude `ask` while no owner stream is
attached and expects it to stay open (to be answered by `answer`, resolved
by the host, closed by `cancel`, `ended`, R4, counted toward 64, etc.) now
gets a pending `no-owner` deny instead. Each such test attaches an owner
stream before its asks (`k.attach(owner, id, 0, "{}")` or the file's
helper) and keeps its assertions; where the attach itself changes a counted
value (pushes, written bytes, `stream/` and `live/` keys, commit counts),
the assertion follows the attach, never weakened past what it proves. Search
all of `kernel/tests/it` (`ask_line`, `ask(`, `"type":"ask"`,
`Kind::Ask`): at least `asks.rs`, `sessions.rs`, `quota.rs`, `restart.rs`,
`s26.rs`, `s28.rs`, `s29_short.rs`, `s29_ceiling.rs`, `adv_s20.rs`,
`adv_s26.rs`, `adv_s28.rs`, `adv_s29.rs`, `streams.rs`, `transcript.rs`,
`idle.rs`, `attach.rs`. A test that asserts an ask stays open with no owner
stream (if any) now asserts the `no-owner` deny. List each changed test in
your final message.
